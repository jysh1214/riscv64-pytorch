Preface

The one idea

When you run torch.compile(model), PyTorch watches your model run once, writes the math down as a graph, and hands it to TorchInductor, which turns it into fast machine code. Here is the single idea this whole book hangs on: every operation in your model ends up as compiled code — the only question is who wrote that code, and when it was compiled. Inductor writes some of it fresh, specialized to your model (that's fusion, the speedup). The rest was written by humans years ago and shipped inside PyTorch (that's ATen). Everything else in this book is detail on that one decision.

The three possible answers, color-coded — these colors mean the same thing on every diagram in this book:

Chapter 1

Where Inductor sits

Inductor is the last stage of torch.compile. Upstream (Dynamo + AOTAutograd) has already flattened your Python into a clean list of tensor operations — an ATen FX graph. Inductor reads that list and emits a small program: a few freshly-written kernels, plus calls to prebuilt ones, plus a wrapper that runs them in order. Click each stage below.

The same flow as a call chain, for reading the source 
compile_fx                          # entry — compile_fx.py:2685
 └─ aot_autograd(...)              # hands fwd/bwd graphs back to Inductor
     ├─ compile_fx_forward         # 2424   (backward: 2558)
     └─ _compile_fx_inner          # 846 — cache lookup, then:
         ├─ _recursive_post_grad_passes      # 570
         ├─ GraphLowering(...).run(*inputs)  # lowering: FX -> IR
         ├─ graph.codegen()                  # scheduler + wrapper -> source
         └─ graph.compile_to_module()        # source -> callable

Forward and backward are split by AOTAutograd's partitioner (partition_fn compile_fx.py:2273); Inductor has no concept of "backward" — it just compiles whatever graph it's handed.

Chapter 2

One model, end to end

Let's compile the core of a transformer block — LayerNorm → Linear → GELU → Linear — and watch 14 ATen operations collapse into 4 calls: two kernels Inductor writes, two library matmuls it doesn't. Every artifact below is real captured output (CPU build, commit 0a327fa).

def mlp_block(x, gamma, beta, w1, b1, w2, b2):
    h = F.layer_norm(x, (x.shape[-1],), gamma, beta)
    h = F.gelu(h @ w1 + b1)
    return h @ w2 + b2          # x:[128,256]  w1:[256,1024]  w2:[1024,256]

layer_norm is already split into var_mean + sub + add + rsqrt + 2×mul + add (7 ops), gelu into 2×mul + erf + add + mul (5 ops), and each @ w + b folded into one addmm (2 ops). Decompositions are chosen by select_decomp_table decomposition.py:972.

lowerEach op becomes an IR node

GraphLowering.run_node graph.py:1829 looks each op up in a dispatch table: var_mean → a Reduction; the elementwise chain → lazy Pointwise nodes; each addmm → an ExternKernel (it will call a library). Chapter 3 is this decision, interactive; Chapter 4 explains the node types.

3

The scheduler fuses everything that shares an iteration space: the 7 LayerNorm ops become cpp_fused_native_layer_norm_0, the 5 GELU ops become cpp_fused_gelu_1. The two addmms are fusion barriers and stay separate. How fusion decides: Chapter 4.

Each fused group becomes one C++/OpenMP kernel. The GELU one, real and nearly complete — five ops, one in-place vectorized loop, no intermediate tensors:

    #pragma omp for
    for (int64_t x0 = 0; x0 < 131072; x0 += 8) {            // 128*1024, 8 floats/AVX vector

    }
}

Chapter 3

The decision: will it fuse?

For each op, Inductor asks three questions, in order. Pick an op and watch it route through the tree — the verdict shows exactly what that op becomes in the final program.

Check any op yourself — the registries are the source of truth

The dispatch table is lowerings lowering.py:124 (filled by @register_lowering lowering.py:534); fallbacks are tagged and tracked in fallbacks lowering.py:129.

import torch, torch._inductor.lowering as L
from torch._inductor.decomposition import decompositions
def classify(op):
    if op in decompositions or op.overloadpacket in decompositions: return "DECOMPOSED"
    fn = L.lowerings.get(op) or L.lowerings.get(op.overloadpacket)
    if fn is None: return "NO LOWERING"
    if getattr(fn, "_is_fallback_handler", False): return "FALLBACK -> aten"
    return "LOWERED -> fused or extern"

Most reliable check of all: read what was actually generated — TORCH_LOGS=output_code python your_script.py.

A gotcha we found by running it
classify() checks decompositions first, so ops with conditional decompositions (mm, add) report DECOMPOSED even when the decomp doesn't fire. On a real build, relu(x @ w) emitted extern_kernels.mm and (x+1).sum() emitted one fused cpp_fused_add_sum_0. When the helper and output_code disagree, trust output_code.
Chapter 4

How fusion happens

Why can Inductor weld 7 ops into one kernel? Because between the graph and the kernel, an op is not code yet — it's a recipe: a function that says how to compute one element. Fusing two ops is just composing their recipes. The art is keeping ops as recipes for as long as possible.

Lazy recipes vs. materialized tensors

A Pointwise node ir.py:1145 stores no tensor — it stores inner_fn(index), a Python function that, given loop indices, emits the scalar steps for one output element (ops.load, ops.add, …). A Reduction ir.py:1309 is the same with an accumulator. To fuse a producer into a consumer, Inductor literally passes the producer's inner_fn as the consumer's loader — function composition, nothing more. Only when a value must exist in memory does it become a ComputedBuffer ir.py:5178 — and fusion across that point is over.

The scheduler's two checks

The Scheduler scheduler.py:4028 repeatedly merges nodes (fuse_nodes scheduler.py:4986) asking two things: is it legal — the consumer reads exactly what the producer wrote, at the same index (can_fuse_vertical scheduler.py:7669), and no dependency cycle is created (scheduler.py:6455); and is it worth it — scored by memory traffic saved (score_fusion_memory scheduler.py:8071). An ExternKernel wrapped as an ExternKernelSchedulerNode scheduler.py:2138 is opaque — nothing fuses through it. That's why the two addmms in Chapter 2 bounded the fusion regions.

The smallest possible demonstration: (x + 1).sum() → one kernel

The Pointwise (+1) feeds the Reduction (sum) at the same indices — textbook vertical fusion into one FusedSchedulerNode scheduler.py:2616. Real captured kernel — the +1 lives inside the reduction loop, and the 1024×1024 intermediate is never allocated:

All three paths end in compiled C++ — the difference is who wrote it and when it was compiled. Green: Inductor, just now, for your shapes. Blue and amber: prebuilt — blue won a race to be there, amber had no rival.

Where call() itself comes from

The wrapper is assembled by PythonWrapperCodegen wrapper.py:1257: the name "call" is fixed at wrapper.py:1378, each kernel call is queued during scheduling as a KernelCallLine wrapper.py:701 (extern calls: wrapper.py:633), and generate() wrapper.py:2120 renders the final source, which is compiled to a module whose call you invoke. For AOTInductor deployment a C++ wrapper replaces the Python one (cpp_wrapper_cpu.py:254).

What "hand-written" really means — the three layers behind an eager ATen kernel

Take the amber example, aten._cdist_forward. "The eager kernel" is three layers:

  • The body (the math) — hand-written C++: native::_cdist_forward Distance.cpp:183, with AT_DISPATCH_FLOATING_TYPES DistanceOpsKernel.cpp:431 stamping the same lambda per dtype, and TensorIterator/Loops.h supplying iteration, broadcasting, and at::vec vectorization for simpler ops.
  • The plumbing — generated at PyTorch build time: the op is declared in native_functions.yaml:4441 (yaml, not C++); torchgen generates the dispatcher registration, at:: API, Python bindings, and autograd glue.
  • Some bodies are just library calls — eager aten::mm is essentially "call BLAS/oneDNN," which is why blue and amber converge in spirit.

And the piece that connects body to plumbing: torch::CppFunction. It is the registration envelope, not the kernel: m.impl(...) wraps your function into a CppFunction library.h:107, which holds a type-erased c10::KernelFunction library.h:298 plus the dispatch key library.h:297 — the dispatcher's filing card. Proof it isn't "the hand-written kernel": the same envelope carries torchgen's generated wrapper_CPU_mm_out_out, and CppFunction::makeFallthrough() library.h:229 contains no kernel at all. One line: the kernel is the letter, CppFunction is the envelope, the dispatch table is the mailbox.

So PyTorch has three code-writing moments: humans (once, in the repo) write kernel bodies; torchgen (at PyTorch build time) writes the plumbing; Inductor (at torch.compile time) writes fused kernels. Eager PyTorch is already partly a code-generation system — Inductor moved codegen from build time to compile time, and from the plumbing into the kernels themselves.

Want to plug your own library into this map (a new vendor backend)? That is Chapter 7.

Chapter 6

Dynamic shapes & caching

One compile can serve many input sizes: Inductor keeps sizes symbolic (s0, s1…) and inserts cheap guards — runtime checks that trigger a recompile when an assumption breaks. And because compiling is expensive, everything is cached so the second run is instant.

Symbolic sizes are managed by SizeVarAllocator sizevars.py:243 (guard_int sizevars.py:957 pins a symbol to a concrete value when it must). The FxGraphCache short-circuits the whole pipeline on a hit, at _compile_fx_inner compile_fx.py:846; below it, compiled kernels are cached on disk.

Data-dependent sizes (the count nonzero returns) can't be guarded — that's one reason such ops live on the amber path in Chapter 5's map.

Chapter 7

Extending the map: plugging in SKL (RISC-V)

Suppose you have a vendor kernel library — SKL for RISC-V — and want compiled models to use it. Nothing about Chapter 5's map changes; you choose which node to plug into. Because the blue and amber paths both end in ATen, there are three attachment points — shown below on Chapter 3's routing ladder, top to bottom. The pink chips are the attachment points — click one for the path it modifies and the actual patch.

Priority — how the three relate

  • Same op, earlier rung wins. mm resolves at Q3, so B's race fires and the amber rung is never consulted — for ops it covers, B has priority over C.
  • A is orthogonal — it has no rung. It sits below every branch and catches whatever arrives, blue or amber, compiled or eager. "Priority" doesn't apply to the floor.
  • C as a graph rewrite (C′) preempts everything. Swapping aten.mm → torch.ops.skl.mm happens before the tree runs, so Q3 never sees an mm. Priority ultimately belongs to whoever edits the graph first.
  • Stacking A + B makes the race SKL vs SKL — with A wired, aten_mm already lands in SKL, so B only wins by wrapper overhead. Choose deliberately rather than stacking.

Only A1 (the BLAS rebuild) remains unapplied.
Chapter 8

The same map on CUDA

Nothing structural changes on a GPU. The map, the decision tree, the race, and the spine — who wrote the kernel, and when — are identical. What changes is every terminus's implementation: green becomes Triton, blue lands in cuBLAS (with a much bigger race), amber lands in CUDA C++ kernels inside libtorch_cuda.so. One honest flag up front: this book's build is CPU-only, so this chapter is source-anchored, not captured — every claim carries a pill, and the one code sketch below is labeled as a sketch.

Two stopwatches on CUDA
Chapter 5's race (which implementation: ATen vs Triton template vs CUTLASS) still runs at compile time, with a bigger field. But every Triton kernel Inductor writes then gets a second, runtime autotune: CachingAutotuner triton_heuristics.py:421 benchmarks launch configurations (XBLOCK, num_warps…) on first run. Different question: not which kernel, but how to launch the kernel Inductor wrote.
Where Chapter 7's approaches land on CUDA
A2 is the same one-line change of dispatch key: TORCH_LIBRARY_IMPL(aten, CUDA, ...). B works identically — your choice just joins an already-crowded race. A1 has no CUDA analog: cuBLAS is a closed vendor library, not a relinkable BLAS ABI slot — the linker seam is CPU-specific. (And mode="reduce-overhead" adds one more layer above everything: the whole call() is captured and replayed as a CUDA Graph — cudagraphify cudagraph_trees.py:496 — eliminating launch overhead without changing the map.)
