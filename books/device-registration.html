Preface

The one idea

PyTorch already knows how to do almost everything; it just does not know about your chip. A device backend is nothing more than a small, fixed set of slots that PyTorch cannot guess on its own — how to allocate memory, how to switch the current device, where the random generator lives, what a few core operators do. Here is the single idea this whole book hangs on: registering a device means filling those slots. Minimum effort means filling only the required ones, and letting one shared dispatch key (PrivateUse1) plus a CPU fallback cover the other ~3500 operators you did not write.

CUDA fills the exact same slots. The only difference is when and where: CUDA is compiled into PyTorch, so its slots are hardwired in-tree and code-generated; your backend lives in its own package and fills the same slots at runtime, through PrivateUse1. Same holes, different filler. That symmetry is the spine — every chapter is a detail on it.

Every slot in this book is tagged with how much work it really costs you. These four tags mean the same thing on every table and widget:

Chapter 1

The workflow, end to end

Six things to write, in order, and then you build and run. Click any step below to see what it does, why PyTorch needs it, the single registration call, the openreg line that proves it, and how small the minimum version can be. The order matters: each step assumes the ones before it.

Steps 1 and 6 are Python (Chapter 5); steps 2–5 are C++ (Chapters 3–4); step 7 is packaging (Chapter 6). Everything tagged free on the scoreboard needs no step at all.

The whole Python side, in three lines

At import time your package runs exactly this. Order is mandatory: name the key first, then hand PyTorch the module, then generate the convenience methods. openreg __init__.py:17:

import torch, torch_openreg
torch.utils.rename_privateuse1_backend("openreg")        # 1. claim + name the key
torch._register_device_module("openreg", torch_openreg.openreg)  # 2. staple module onto torch.openreg
torch.utils.generate_methods_for_privateuse1_backend(for_storage=True)  # 3. tensor.openreg(), .is_openreg

The C++ registrations (steps 2–5) are not called from Python — they run automatically as static initializers when your shared library is loaded. You never call them; linking the .cpp in is what arms them.

Chapter 2

What "register" actually means

"Registering" is not magic — it is dropping a pointer into a global table. PyTorch keeps a handful of tables indexed by device type: one for guards, one for allocators, one pointer for hooks, a slot per operator. To register a device is to write your objects into those slots for the PrivateUse1 entry. After that, every piece of generic PyTorch code finds your code by looking up the table — it never needs to know it is talking to your chip.

Pick a line of user code below and watch which slot answers it. This is the payoff of registration: ordinary user code routes, with no special-casing, into the slots you filled.

The tables, concretely

None of these are abstractions — they are plain global arrays/pointers you can point at:

  • Guards: a fixed array indexed by DeviceType; C10_REGISTER_GUARD_IMPL writes a new-ed instance into your slot (DeviceGuardImplInterface.h:379).
  • Allocators: a table keyed by DeviceType; REGISTER_ALLOCATOR calls SetAllocator (Allocator.h:299).
  • Hooks: a single process-global pointer set once by RegisterPrivateUse1HooksInterface (PrivateUse1HooksInterface.cpp:8).
  • Operators: the dispatcher's per-operator table; TORCH_LIBRARY_IMPL(aten, PrivateUse1, m) writes one kernel into the PrivateUse1 column (OpenRegMinimal.cpp:119).

CUDA writes into the very same tables, just under the CUDA key instead of PrivateUse1 — its registrations are emitted by codegen and compiled into libtorch_cuda.

Chapter 3

The C++ runtime slots

Four C++ objects do the heavy lifting: the guard (drive the device context), the allocator (get and free bytes), the hooks (answer generic questions), and the generator (random numbers). For minimum effort, openreg shows that each can be small — and that the parts you skip simply throw a clear error if anyone reaches them, rather than failing the build.

must write The device guard

Feynman: PyTorch needs a generic way to ask "which device am I on?", "switch to device 1 and back", "give me a stream". It cannot call your driver directly, so you write one object with those methods and drop it in the guard table. The RAII DeviceGuard users rely on is built on top.

Subclass c10::impl::DeviceGuardImplInterface, mark it final, set static_type = DeviceType::PrivateUse1, and register it:

struct OpenRegGuardImpl final : public c10::impl::DeviceGuardImplInterface { /* device + stream + event methods */ };
C10_REGISTER_GUARD_IMPL(PrivateUse1, OpenRegGuardImpl);

Minimum effort: implement the six device methods (type, getDevice, setDevice, uncheckedSetDevice, exchangeDevice, deviceCount) plus getStream/exchangeStream. The event methods have throwing default bodies, so a backend that ignores streams/events still compiles — code that touches them just errors at runtime. OpenRegGuard.cpp:6 · interface DeviceGuardImplInterface.h:60 · CUDA twin CUDAGuardImpl.h:23

Gotcha
deviceCount() and uncheckedSetDevice() are noexcept by contract: deviceCount must report 0 on a driver error, never throw. And the struct must be final so the compiler can devirtualize the hot exchangeDevice call.
must write The allocator (and stub ok pinned memory)

Feynman: tensor bytes have to come from somewhere. You write an allocator whose allocate() calls your runtime's malloc and returns a self-freeing DataPtr, then drop it in the allocator table for PrivateUse1.

REGISTER_ALLOCATOR(c10::DeviceType::PrivateUse1, &g_allocator);

Minimum effort: a plain malloc/free is fine — openreg's allocator does no caching (emptyCache and recordStream are no-op stubs) and it still works. The pinned/host allocator is stub ok: register it with REGISTER_HOST_ALLOCATOR(at::kPrivateUse1, ...) and expose it through the hooks, or skip it and pin_memory() simply will not accelerate. OpenRegDeviceAllocator.cpp:273 · host OpenRegHostAllocator.cpp:6

CUDA does not use the macro: it calls SetAllocator(kCUDA, r, /*priority=*/1) so the caching allocator (or cudaMallocAsync) can override the default (CUDACachingAllocator.cpp:5381). You do not need that for a first backend.

must write The hooks interface

Feynman: when PyTorch wants a general fact about your device — "are you available?", "how many devices?", "give me the default generator", "is this pointer pinned?" — it does not call a kernel. It calls hooks: one object answering all these questions, handed to PyTorch once.

struct OpenRegHooksInterface : public at::PrivateUse1HooksInterface { /* overrides */ };
at::RegisterPrivateUse1HooksInterface(new OpenRegHooksInterface());  // once, in a static init

Minimum effort: override the few hooks you actually use (e.g. getDefaultGenerator, getPinnedMemoryAllocator, isPinnedPtr). Every hook you skip has a default that throws a clear "not implemented" at call time — so an unfinished hooks object still links and runs. OpenRegHooks.cpp:6 · base PrivateUse1HooksInterface.h:15

Myth, debunked
You may read that hasPrimaryContext is a pure-virtual you must override to compile. That is only true of the abstract AcceleratorHooksInterface. The class you actually subclass, PrivateUse1HooksInterface, already supplies a throwing default for it (PrivateUse1HooksInterface.h:15), so your subclass compiles without it — it just throws if called. Override it for correct behavior, not to satisfy the compiler.
Gotcha
Register exactly once, and heap-allocate it (new) — core keeps the raw pointer for the whole process. A second registration hard-fails the process (PrivateUse1HooksInterface.cpp:8).
stub ok The generator (RNG)

Feynman: random ops need a per-device "dice roller" you can seed for reproducibility. The cheapest version reuses the CPU one: openreg derives its generator from at::CPUGeneratorImpl and just stamps the PrivateUse1 device/key on it — so randomness actually runs on CPU, which is fine to start.

Wire it through the hooks (the modern path): override getDefaultGenerator (one shared instance per device) and getNewGenerator (a fresh one). That is all torch.manual_seed needs. OpenRegHooks.h:85 · impl OpenRegGenerator.cpp:9

There is an older REGISTER_GENERATOR_PRIVATEUSE1 macro; it is deprecated and warns. Use the hooks. A real accelerator later implements the full GeneratorImpl contract (like CUDAGeneratorImpl.cpp:50) so randomness runs on-device.

Chapter 4

Operators with (almost) no kernels

PyTorch has ~3500 operators. The minimum-effort trick is to hand-write only a tiny core — the ones that allocate or move bytes — and register a single catch-all fallback that quietly ships every other op to the CPU, runs it there, and copies the result back. You replace fallbacks with native kernels later, one at a time, as you need speed.

Pick an operator and watch how it routes:

The two registration blocks that make this work — the minimal kernels, and the wildcard fallback:

TORCH_LIBRARY_IMPL(aten, PrivateUse1, m) {        // ~10 core ops you must write
    m.impl("empty.memory_format", wrapper_empty_memory_format);
    m.impl("_copy_from", ...);  // view, as_strided, _local_scalar_dense, ...
}
TORCH_LIBRARY_IMPL(_, PrivateUse1, m) {           // the wildcard "_" namespace = every other op
    m.fallback(torch::CppFunction::makeFromBoxedFunction<&wrapper_cpu_fallback>());
}

OpenRegMinimal.cpp:119 (kernels) · OpenRegMinimal.cpp:141 (fallback). Contrast CUDA, which writes no such blocks: it lists dispatch: CUDA: empty_cuda in native_functions.yaml:2324 and codegen emits the registrations. Out-of-tree, there is no codegen — you hand-write TORCH_LIBRARY_IMPL.

Why _copy_from is the one kernel you cannot get wrong

_copy_from is the engine of Tensor.copy_ and of all cross-device transfers — which means the CPU fallback itself rides on it (move inputs to CPU, run, copy back). If it is wrong, the fallback breaks, and with it the other ~3490 ops. Get this one right first. Minimal.cpp:81

Two things you get for free, and one trap
  • free Autograd. Because autograd is always on, even forward-only ops dispatch through AutogradPrivateUse1. PyTorch ships a generic fallback there that lets the forward pass through and only errors if a real backward is requested — so training-free inference works with zero autograd code. VariableFallbackKernel.cpp:111
  • later Blocklist. The fallback can refuse specific ops so they raise a clear error instead of silently running slowly on CPU — openreg does this for abs to force a native kernel. Minimal.cpp:167
  • later STUB ops (TensorIterator kernels like abs_stub) are a two-step trap: registering REGISTER_PRIVATEUSE1_DISPATCH(abs_stub, ...) does nothing unless you also register the structured out-variant abs.out under PrivateUse1. OpenRegExtra.cpp:137
Trap
The fallback lives in the wildcard _ namespace and uses m.fallback(), not m.impl(), and must be a boxed function (OperatorHandle, Stack*). A typed kernel will not work as a fallback.
Chapter 5

The Python surface

Three lines make torch.mydev.* and tensor.mydev() work, plus a small Python module of runtime functions. The payoff is big: once the key is named, your backend shows up under the generic torch.accelerator.* API automatically.

Step 1, name the key, must come first — it is what makes "mydev" a valid device string and aliases the profiler and autograd enums. Then hand PyTorch your module and generate the convenience methods:

torch.utils.rename_privateuse1_backend("openreg")
torch._register_device_module("openreg", torch_openreg.openreg)
torch.utils.generate_methods_for_privateuse1_backend(for_storage=True)

backend_registration.py:76 · __init__.py:2842 · backend_registration.py:409

Your device module just needs the handful of names PyTorch and torch.accelerator look up by convention. Minimum set:

FunctionWhat it answers

set_device(i)switch the active device

These typically forward to your C extension (e.g. torch_openreg._C._get_device_count()). openreg's module: __init__.py:36.

free torch.accelerator, for nothing
Once the key is registered, at::accelerator::getAccelerator picks PrivateUse1 as the active accelerator, so torch.accelerator.current_accelerator(), torch.accelerator.device_count() and friends route to your module with no extra Python wiring. DeviceAccelerator.cpp:8
Gotcha
The ordering is enforced and the rename is once-per-process. Call rename_privateuse1_backend before the other two, and never twice — a second call (or a different name, or an in-tree name like "cuda") raises from C++ (DeviceType.cpp:140).
Chapter 6

Build, install, run

The C++ registrations only exist if their .cpp files are compiled into a library that actually loads. So packaging is the last required step: build the native library, link it into a Python _C extension, and (optionally) declare an entry point so import torch loads you automatically.

  1. Build the native library. A CMakeLists.txt globs your csrc/*.cpp so every registrar (guard, allocator, hooks, ops) is compiled in — drop a new .cpp under csrc/ and it is picked up, no per-file edit. CMakeLists.txt:3
  2. Link it into a Python _C extension. setup.py declares the extension and ships the .so. setup.py:116
  3. Declare autoload (optional but recommended) so users never type import torch_openreg. setup.py:145
  4. Install and smoke-test: pip install -e ., then the e2e check below.
import torch, torch_openreg
x = torch.empty(3, device="openreg")   # allocator + guard + empty kernel
y = (x + 1).cpu()                      # add via CPU fallback, _copy_from back
print(torch.accelerator.current_accelerator())  # device(type='openreg')  -- free

If those three lines run, every required slot is filled. That is a registered device.

The two libraries (a common point of confusion)

openreg builds two CMake libraries, which is worth understanding so you put files in the right place:

  • torch_openreg — the runtime library: guard, allocator, hooks, generator, ops, serialization. Built from csrc/ (csrc/CMakeLists.txt:3).
  • torch_bindings — the Python _C extension (the PyMethodDef table). It links torch_openreg, so loading _C transitively loads the runtime library and fires all its static registrars.

So the runtime registrations live in torch_openreg, not in the _C extension; the _C extension only exposes Python-callable helpers. CUDA, by contrast, is imported unconditionally inside the torch package (from torch import cuda, __init__.py:2300), so it needs no entry point.

Autoload: a no-op entry point, and a build-time guard

The entry point in the torch.backends group points at a function that is a deliberate no-op — all the real work happens as import side effects (the three lines from Chapter 5) when PyTorch imports your package to reach that function. PyTorch's autoload driver scans these at import torch. __init__.py:3011

Gotcha
Any build script that imports torch while your half-built backend is installed will autoload it and fail. Set TORCH_DEVICE_BACKEND_AUTOLOAD=0 before import torch in build/codegen scripts — openreg's setup.py does exactly this. Also: a crash in your entry point breaks plain import torch for everyone who installed you, so keep it robust.

Chapter 8

Worked example: RVO + TinyLlama-1.1B

Let's actually do it. RVO is a made-up accelerator; we register it with the least code that works, then actually run TinyLlama-1.1B on it. The trick that makes it tiny: RVO's device memory is just host memory, so the ~10 core ops are one-liners and every real model op (matmul, attention, RMSNorm, softmax) rides the CPU fallback. The model runs correctly — at CPU speed — while genuinely dispatching as device="rvo".

The whole package: six small files

RVO is even leaner than openreg: one C++ file built by torch.utils.cpp_extension (no CMake), plus the three-line Python registration. The shape:

rvo/
  rvo/__init__.py     # rename_privateuse1_backend + _register_device_module + generate_methods
  rvo/_device.py      # device_count / current_device / set_device / is_available
  csrc/rvo.cpp        # guard + allocator(==malloc) + hooks + ~10 ops + CPU fallback
  setup.py            # CppExtension("rvo._C", ["csrc/rvo.cpp"]) + autoload entry point
  run_tinyllama.py    # real TinyLlama-1.1B, runs end to end (the live proof)
  run_tiny_llama.py   # tiny from-scratch model, instant smoke test (no download)

The registration is the same three lines from Chapter 5; the C++ is the same four registrars from Chapter 3, collapsed because device memory is host memory:

# rvo/__init__.py
torch.utils.rename_privateuse1_backend("rvo")
torch._register_device_module("rvo", _device)
torch.utils.generate_methods_for_privateuse1_backend(for_storage=True)

// csrc/rvo.cpp -- the four registrars, bodies trivial because memory == host memory
C10_REGISTER_GUARD_IMPL(PrivateUse1, RVOGuard);              // single-device, all no-ops
REGISTER_ALLOCATOR(c10::DeviceType::PrivateUse1, &g_alloc);  // allocate() == malloc()
at::RegisterPrivateUse1HooksInterface(new RVOHooks());        // hasPrimaryContext -> true
TORCH_LIBRARY_IMPL(aten, PrivateUse1, m) { m.impl("empty.memory_format", ...); /* ~10 ops */ }
TORCH_LIBRARY_IMPL(_, PrivateUse1, m) { m.fallback(makeFromBoxedFunction<&cpu_fallback>()); }

Each registrar is the genuine API from Chapter 3: OpenRegGuard.cpp:6, OpenRegDeviceAllocator.cpp:273, OpenRegHooks.cpp:6, OpenRegMinimal.cpp:119 / :141. Copy the real op bodies (especially _copy_from) from openreg.

RVO isn't a new design — it's OpenReg's mechanism, trimmed, filling the same slots CUDA fills in-tree. Construct by construct:

Two nuances: RVO marks getStream/exchangeStream noexcept like OpenReg (CUDA omits it — both legal), and the skeleton stubs streams/events and shows 2 of the ~10 core ops.

Run TinyLlama-1.1B

Once rvo is installed, running a real LLM is one .to("rvo") plus a short greedy loop. TinyLlama-1.1B is ungated, so this genuinely downloads and runs:

# run_tinyllama.py (essence)
import torch, rvo                                 # importing rvo registers the device
from transformers import AutoModelForCausalLM, AutoTokenizer
tok   = AutoTokenizer.from_pretrained("TinyLlama/TinyLlama-1.1B-Chat-v1.0")
model = AutoModelForCausalLM.from_pretrained(
            "TinyLlama/TinyLlama-1.1B-Chat-v1.0", dtype=torch.float32,
            attn_implementation="eager").eval().to("rvo")   # eager attn -- see note below
ids = tok(prompt, return_tensors="pt").input_ids.to("rvo")
for _ in range(24):                                # 5-line manual greedy decode
    nxt = model(ids).logits[:, -1].argmax(-1, keepdim=True)
    ids = torch.cat([ids, nxt], dim=1)
print(tok.decode(ids[0]))

Needs pip install transformers + a ~2.2 GB download (no Hugging Face gating). We ran exactly this against openreg, RVO's in-tree twin — captured below.

Why it runs: the dispatch story

A Llama forward is an embedding, a stack of (RMSNorm, rotary attention, SwiGLU MLP), and a final projection. RVO implements none of that math — only the six memory/layout ops. Everything else routes to the CPU fallback. Probed live on the device:

ATen opHas a PrivateUse1 kernel?Runs as
empty.memory_format, empty_strided, _copy_from, view, as_strided, _local_scalar_denseyescore kernel on device
mm, addmm, bmm (all the Linears + attention scores)noCPU fallback
embedding, _softmax, silunoCPU fallback
mul, rsqrt, mean (RMSNorm, rotary), cat, argmax, triunoCPU fallback

That is the spine in one table: the device supplies memory and layout; the fallback supplies math; Llama runs. You make it fast later by replacing fallback rows with real kernels (Chapter 7), the heaviest first (mm/addmm).

Two rough edges for a brand-new backend
An op-by-op diff against CPU shows every op is bit-exact on the device except the fused scaled_dot_product_attention (maxdiff ~2.6) — so TinyLlama is loaded with attn_implementation="eager" (plain matmul + softmax, which the fallback reproduces exactly). Second, HF generate() mixes a CPU pad-token tensor with device tensors, so we drive a 5-line manual greedy loop instead. Both are gaps a real backend closes (implement SDPA; fix the stray CPU tensor) — neither stops the model from running.
